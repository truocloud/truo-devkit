# Image packages

URL builder and framework loaders for [img.truo.cloud](https://docs.truo.cloud/images).

| Package | What it is |
|---|---|
| [`@truocloud/img`](packages/url) | the URL builder — `buildUrl`, `srcset`, `parseUrl`, and signing behind a second entrypoint |
| [`@truocloud/img-next`](packages/next) | `next/image` loader |
| [`@truocloud/img-nuxt`](packages/nuxt) | `@nuxt/image` provider |
| [`@truocloud/img-angular`](packages/angular) | `NgOptimizedImage` loader |
| [`unpic-src/`](unpic-src) | provider for [unpic](https://unpic.pics), not published — the source of an upstream PR |

## Why this is a workspace of its own

It sits outside `packages/*` on purpose, with its own lockfile and its own release
tag (`img-vX.Y.Z`, which does not match the `v*` trigger of the other one):

- **the version tracks a different thing.** The three packages under `packages/*`
  share a version because they all come out of the same commit of the same OpenAPI
  spec. These come out of the URL contract, which moves independently.
- **a loader must not bundle its framework.** The root build script has no
  externals — correct for a self-contained SDK, fatal for something that would end
  up carrying a copy of `next` or `@angular/common`.
- **CommonJS.** `next.config.js` is still CJS in most real projects, so a loader
  that cannot be `require`d is a loader nobody installs. The other packages are
  ESM-only.
- **their CI gate is not ours.** `sync:spec --check` hits the network and would
  block a loader fix on a spec these packages never touch.

Same reasoning that already keeps `docs/` out of the workspace.

## `fixtures/urls.json` — the thing that keeps four implementations honest

The same URL string is built by code in three languages and interpreted by a
fourth:

```
@truocloud/img (TypeScript) ─┐
each framework loader ───────┼─→  https://img.truo.cloud/i/acme/uploads/photo.jpg?f=auto&w=800
class-url-builder.php ───────┘                    │
                                                  └─→ img.truo.cloud (Bun) interprets it
```

They cannot be allowed to disagree, and the ways they disagree are not obvious:
PHP's `rawurlencode` escapes `!*'()` and JavaScript's `encodeURIComponent` does
not, so `mi foto (1).jpg` — literally how WordPress names a duplicated upload —
comes out as two different URLs, two CDN cache entries and two different
signatures.

So the vectors are **generated by the service** from its own parser and signer,
served at `https://img.truo.cloud/fixtures/urls.json`, and every implementation
tests against them. Each vector carries a `why`: it is there because there is a
concrete way two reasonable implementations produce different output, not to make
a number go up.

```bash
bun run sync:fixtures          # pull the current contract
bun run sync:fixtures --check  # fail if the local copy is stale (CI runs this)
```

`packages/url/src/names.ts` is generated from the same file — hand-copying a
90-row alias table is how a parameter ends up silently ignored and a full-size
image billed as a thumbnail.

## Commands

```bash
bun install
bun run sync:fixtures --check   # the contract has not moved
bun run gen:check               # the generated name table matches it
bun run typecheck
bun test
bun run build                   # ESM + CJS + .d.ts, with size budgets enforced
```

Size budgets are a failing test, not a dashboard: this is code that runs in every
visitor's browser, and the moment it stops being obviously small is the moment an
upstream maintainer reviewing our provider closes the tab.

| | measured | limit |
|---|---|---|
| `@truocloud/img` | 2143 B | 2400 B |
| `@truocloud/img/sign` | 724 B | 900 B |
| each loader | 418-587 B | 700 B |

*(minified and gzipped — we publish unminified, so the published file size says
nothing about what a visitor downloads)*

## Releasing

```bash
git tag img-v0.1.0 && git push origin img-v0.1.0
```

`release-img.yml` re-runs every gate, writes the version into the four
`package.json` files, and publishes with provenance in dependency order — core
first, because the loaders declare an exact dependency on it and publishing a
loader first leaves a version npm cannot resolve.
