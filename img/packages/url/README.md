# @truocloud/img

URL builder for [img.truo.cloud](https://docs.truo.cloud/images). Zero
dependencies, ~2 KB gzipped, ESM and CommonJS.

```bash
npm install @truocloud/img
```

```ts
import { createTruoImg } from "@truocloud/img";

const img = createTruoImg({ pid: "acme" });

img.url("uploads/photo.jpg", { width: 800, format: "auto" });
// https://img.truo.cloud/i/acme/uploads/photo.jpg?f=auto&w=800

img.srcset("uploads/photo.jpg", { transform: { format: "auto" } });
// …?f=auto&w=640 640w, …?f=auto&w=828 828w, …?f=auto&w=1200 1200w, …
```

`pid` is your tenant's public id, shown in the console under **Images →
Endpoint**. It is not a secret: it appears in every image URL on your site.

## Two ways to name a source

```ts
img.url("uploads/photo.jpg");                 // a path on your own origin
img.url("https://example.com/photo.jpg");     // proxied through /fetch/
img.url(anAlreadyBuiltTruoUrl, { width: 800 }); // rewritten, not wrapped again
img.url("data:image/gif;base64,…");           // returned untouched
```

The last two matter more than they look. Framework loaders and CMS filters run
over the same markup twice more often than anyone expects, and wrapping twice
produces a URL that works, costs double and is unreadable in a bug report.

## Responsive images

```ts
<img
  src={img.url("uploads/photo.jpg", { width: 1200 })}
  srcSet={img.srcset("uploads/photo.jpg", { transform: { format: "auto" } })}
  sizes={img.sizes([[768, "100vw"], [1200, "50vw"]], "33vw")}
/>
```

**Do not skip `sizes`.** With a `srcset` and no `sizes`, the browser assumes
`100vw` and downloads the largest candidate on a phone — the single most common
way a "responsive images" setup ends up slower than the plain `<img>` it replaced.

The default ladder is five widths (`640, 828, 1200, 1600, 2048`), not eight. The
service caches a transformation on its second identical request, so every width
costs two transformations before it starts being served from cache: with eight
widths, a page with five images costs 80 transformations on the first visit.

## Signed URLs

Signing lives behind a second entrypoint so a bundler never pulls it — or your
secret — into browser code:

```ts
import { signUrl } from "@truocloud/img/sign";

const url = await signUrl(img.url("uploads/private.jpg", { width: 800 }), {
  secret: process.env.TRUO_IMG_SECRET,   // server-side only
});
```

Omit `ttl` and the URL does not expire, which is what static HTML, a CMS and a
CDN all need. The signature covers the **path as well as the query**, so nobody
can swap the file and keep it valid.

## `format: "auto"` and when not to use it

`f=auto` picks avif or webp from the browser's `Accept` header and answers
`Vary: Accept`. That is correct HTTP, and it is fragile behind a CDN you did not
configure: `Accept` has very high cardinality, and some CDNs ignore `Vary` on
images unless you turn it on (Cloudflare calls it "Vary for Images").

If your images sit behind a third-party CDN, pin `format: "webp"`. A slightly
larger file that is always the right one beats an avif served to a browser that
cannot decode it.

## Reading a URL back

```ts
import { parseUrl } from "@truocloud/img";

parseUrl("https://img.truo.cloud/i/acme/uploads/photo.jpg?f=auto&w=800");
// { pid: "acme", mode: "endpoint", src: "uploads/photo.jpg", transform: { f: "auto", w: "800" }, … }
```

`buildUrl(parseUrl(u).src, parseUrl(u).transform, cfg) === u` for every URL this
package produces — the round trip [unpic](https://unpic.pics) requires.

## The shared fixture

`@truocloud/img/fixtures/urls.json` ships with this package. It is generated by
the service from its own parser and signer, and it is what keeps this builder,
the WordPress plugin's PHP builder and the service itself emitting byte-identical
URLs. If your own integration builds these URLs, test against it.
